# i18n protocol — `opengwt.i18n/1`

The message format, file layout, fallback rules and conformance suite shared by the Python server
and the Unity client. Companion to [ADR 0006](../adr/0006-i18n-keys-and-unity-localization.md).
Two renderers implement this document; the conformance suite (section 7) is what keeps them equal.

## 1. Files

```
data/i18n/
  en/cards.yaml        card and faction texts        (base language)
  en/abilities.yaml    card text templates (section 10)
  en/ui.yaml           client strings
  en/errors.yaml       error and prompt texts
  zh-CN/…              same domains, same keys
  ru/…
  conformance.yaml     renderer conformance cases, run by server and client
```

Each domain file is a flat YAML map from key to message. Domains only organise the files; at
runtime all domains of a locale are one table. Locales are BCP 47 tags: `en`, `zh-CN`, `ru`.
`en` is the base language: every key exists there.

## 2. Keys

Keys match `^[a-z][a-z0-9-]*(\.[a-z0-9-]+)*$`. Conventions:

| Prefix | Example | Used by |
| --- | --- | --- |
| `card.<id>.name`, `card.<id>.text` | `card.u-0007.name` | content pack, client |
| `faction.<id>.name` | `faction.placeholder-a.name` | content pack, client |
| `tag.<id>.name` | `tag.tag-a.name` | content pack, client |
| `status.<status>.name`, `.text` | `status.banish-on-leave.name` | client — the words shown for a status (`cards.md` §9) |
| `row-effect.<effect>.name`, `.text` | `row-effect.damage-weakest.name` | client — the words shown for a row effect (`cards.md` §10) |
| `ui.<screen>.<element>` | `ui.board.pass-button` | client |
| `error.<code>` | `error.illegal-intent` | server-rendered fallback, client |
| `error.deck.<rule>` | `error.deck.too-many-copies` | client — a deck-building problem, rendered with its `params` (`match.md` §10, `cards.md` §12) |
| `choice.<action>`, `choice.place` | `choice.play-from-deck` | pending-choice prompts (`match.md` §7) |
| `ability.<action>….text` | `ability.draw.text` | generated card text: one sentence per ability (section 10) |
| `ability.<part>.…` | `ability.target.chosen.opponent` | generated card text: the phrases sentences are made of (section 10) |

Vocabulary ids inside a key keep their words but write underscores as hyphens, since keys have
none: `status.banish-on-leave.name`, `choice.play-from-deck`.

A **plural variant** is a key with one of the suffixes `.zero`, `.one`, `.two`, `.few`, `.many`,
`.other` appended to a base key. If a locale defines any variant of a base key it must define
`.other`. A locale without plural forms may define just the base key.

## 3. Message syntax

A message is literal text with placeholders.

| Form | Meaning |
| --- | --- |
| `{name}` | Insert the parameter `name`. Names match `[a-z][a-z0-9_]*`. |
| `{{` and `}}` | A literal `{` and `}`. |
| anything else | Literal text, including a `{` or `}` that does not form one of the above. |

A placeholder whose parameter is absent is left in the output verbatim, braces included, so the
gap is visible to testers instead of silently disappearing. There are no format specifiers, no
conditionals and no nesting. If a sentence cannot be written with this, the answer is a different
key or a different sentence, not a bigger syntax.

## 4. Parameters

Parameters are a map from name to **integer** or **string**. Nothing else is allowed; booleans
and floats are a validation error at the call site.

- Integers render as decimal digits with a leading `-` when negative; no grouping, no locale
  digits.
- Strings render verbatim, except:
  - a string starting with `@` is a **reference**: `@card.u-0007.name` is replaced by that key's
    message in the current locale, resolved with the fallback chain of section 6 and inserted
    as-is — its own placeholders and references are not processed;
  - a string starting with `@@` renders as the string from its second character on (`@@name`
    → `@name`).

## 5. Plurals

If the parameters contain an integer named `count`, the renderer computes the CLDR plural
category of `|count|` for the locale and looks up the variants before the base key (section 6).
Only integer rules are needed; the categories per supported locale are:

| Locale | Rule for `n = |count|` |
| --- | --- |
| `en` | `one` if `n == 1`, else `other` |
| `zh-CN` | always `other` |
| `ru` | `one` if `n % 10 == 1` and `n % 100 != 11`; `few` if `n % 10` in 2..4 and `n % 100` not in 12..14; else `many` |

Adding a locale means adding its rule to both renderers and conformance cases that exercise it.
A parameter named `count` that is not an integer is a validation error.

## 6. Lookup and fallback

Resolution is **locale-major**: every candidate key is tried in the requested locale before any
is tried in the fallback locale.

```
for locale in [requested, "en"]:
    for candidate in [key + "." + category, key + ".other", key]:   # the first two only when count is given
        if candidate in table[locale]: return table[locale][candidate]
return key                                   # missing everywhere: the key itself, unrendered
```

Consequences worth knowing:

- a locale that defines only `.other` (or only the base key) never falls through to English for
  a plural it does not distinguish;
- a message that falls back to English still resolves its `@` references locale-major, so a
  mixed-language sentence is possible and is the intended behaviour, not a bug;
- a missing key renders as the key, and the server counts it (`i18n_missing_key{locale,key}`)
  while the client shows it, so it is found in testing.

## 7. Conformance suite

`data/i18n/conformance.yaml` carries its **own** small tables so that the cases test the renderer,
not the content. Both renderers run every case in CI.

```yaml
schema: opengwt.i18n-conformance/1
tables:
  en:
    ui.hand.count.one: "{count} card in hand"
    ui.hand.count.other: "{count} cards in hand"
  ru:
    ui.hand.count.one: "{count} карта в руке"
    ui.hand.count.few: "{count} карты в руке"
    ui.hand.count.many: "{count} карт в руке"
    ui.hand.count.other: "{count} карт в руке"
cases:
  - { locale: ru, key: ui.hand.count, params: { count: 22 }, expected: "22 карты в руке" }
```

A complete suite covering every rule in this document is in
[`examples/i18n-conformance.yaml`](examples/i18n-conformance.yaml); the real file starts as a copy
of it and grows with every renderer bug found.

## 8. Server

- **Serving tables.** `GET /content/i18n` → `{locales: [...], pack_hash}`;
  `GET /content/i18n/{locale}` → the merged table of that locale. `ETag` is the pack hash;
  `If-None-Match` is honoured. The tables are also inside the content pack.
- **Locale negotiation**, in order: the `locale` field of the player's profile (`PATCH /me`);
  the best supported match of `Accept-Language`; `en`.
- **Errors.** Every error, HTTP or WebSocket, carries `code`, `message_key`, `params` and
  `message`, where `message` is `message_key` rendered with `params` in the negotiated locale.
  Clients that know the key render it themselves and ignore `message`.
- **Nothing else is rendered on the server.** Events, views, stored records, logs and metrics
  carry keys and parameters.

## 9. Client

- Renders every string it shows with its own implementation of sections 3–6.
- Fetches the table for its locale after `hello` when the pack hash changed, and caches it.
- Uses the server's `message` only when `message_key` is unknown to it.
- Selects the locale from the system by default, lets the player override it, and writes the
  override to the profile so server-rendered fallbacks match.
- Provides a font fallback chain covering Latin, Cyrillic and CJK, and lays out with room for the
  roughly thirty percent expansion Russian shows over English.

## 10. Generated card text

The compiler (`opengwt.data`) builds `card.<id>.text` from the card's definition for every locale
that lacks the key; an explicit `card.<id>.text` always wins, locale by locale, so an override in
one language does not force one in the others. Card text and card behaviour cannot drift apart,
and translating a new card set means translating the templates once — `data/i18n/<locale>/
abilities.yaml` — plus the names and whatever overrides a designer wants. `opengwt-data
card-text` prints what every card gets, and `--ignore-explicit` what the generator would say
where an explicit text exists.

A generated text is sentences joined by `ability.join.sentences`, in this order: the row the card
is restricted to (`ability.card.row-only.<row>`, or `ability.card.stratagem-row.<row>`), the
opponent's side (`ability.card.opponent-side`), armour (`ability.card.armor`), each innate status
(`ability.card.status.<status>`), a leader's provision bonus (`ability.card.provision-bonus`), then
the abilities grouped by trigger in the order the triggers first appear. A plain unit gets an
empty text.

- **Groups.** The abilities of one trigger render as one clause: `ability.when.<trigger>` with the
  sentences as `{effect}`. A special's `on_play` and every `while_on_board` ability have no
  clause; `on_activate` renders through `ability.activate.charges`, `.cooldown` or
  `.charges-cooldown` from the card's `activation`, followed by `ability.activate.ready-on-play`
  when it applies. `on_ally_played` takes the `trigger_unit` condition as its `{filter}`.
- **Conditions.** Consecutive abilities with the same other conditions share
  `ability.if.text` — `{condition}` is their parts (`ability.if.<condition>`, and
  `ability.is.<filter>` for `if.this`) joined by `ability.if.and`.
- **Sentences.** Each ability is `ability.<action>.text`, or a variant for its parameters
  (`ability.add-status.<status>[.timed].text`, `ability.draw.opponent.text`,
  `ability.set-row-effect.<effect>.text`, `ability.clear-row-effect[.<only>].text`,
  `ability.add-charges.<to>.text`, `ability.continuous-boost.<scope>.text`,
  `ability.create.<noun>.text`, `ability.remove-statuses[.all].text`).
- **Phrases**, rendered first and inserted as parameters: `{target}` from
  `ability.target.<units>[.<side>]` (`.self-other` and `.both-other` for `all` from a card on the
  board, which is never its own target); `{rows}` from `ability.rows.…`; `{cards}` from
  `ability.cards.<pick>.<noun>` with `<noun>` one of `unit`, `special`, `artifact`, `card` or `copy`
  (for `same_id_as_this`); `{from}` from `ability.from.<zone>.<side>`; `{place}` from
  `ability.place.…`; `{filter}` from the qualifiers `ability.where.<filter>` — statuses as
  `ability.state.<status>`, tags as `@tag.<id>.name` — joined by `ability.join.list` and wrapped in
  `ability.where.wrap`, or empty; a status list from `ability.status.<status>`; a new card's name
  as the reference `@card.<id>.name`. Lists end with `ability.join.or` or `ability.join.and`.
- **Numbers.** `{amount}`, `{cooldown}` and the like are the ability's integers; `{count}` is
  always the number the sentence agrees with — the amount of damage, the cards drawn, the random
  units, the turns of a status — so plural variants (section 5) follow it.
- **The recipient twin.** Damage, armour, a base-power raise, drain, a shield and immunity name
  their target as the *recipient*; everything else as the *object*. A locale whose grammar marks
  the two differently — Russian puts the recipient in the dative — defines `ability.target-to.…`
  twins of every `ability.target.…` phrase, and recipient sentences use them; a locale without
  them uses the plain phrases. A locale with any twin must define all of them.

A rendered phrase is inserted literally — one starting with `@` is escaped as `@@` — so no text a
designer writes is ever read as a reference. A template key missing from every table is a
compiler error naming the cards that need it; section 2's completeness rule covers the rest.

## 11. Versioning

The format is versioned by this document's title. Any change to sections 3–6 is a breaking change
for both renderers: bump the version, update both, extend the conformance suite in the same pull
request.
